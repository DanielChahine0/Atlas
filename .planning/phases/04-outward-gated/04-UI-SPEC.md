# Phase 4 — UI Design Contract

> Visual and interaction contract for the Phase 4 confirmation-gate surfaces.
> Generated by gsd-ui-researcher. Verified by gsd-ui-checker.
>
> **Scope note.** Atlas is a backend multi-agent orchestrator — there is no web app, no SPA,
> no dashboard UI in this phase. The ENTIRE user-facing surface is:
>
>   1. The **token-gated confirm page** — a server-rendered HTML page opened from a push link.
>   2. The **ntfy push notification** copy — the push body + HTTP action buttons.
>
> Both are served from a Cloudflare Worker as plain server-rendered HTML/CSS (no build step,
> no component library dependency). The Vault/Obsidian dashboard is out of scope for this phase.

---

## Design System

| Property | Value | Source |
|----------|-------|--------|
| Tool | none — plain server-rendered HTML/CSS | D4-00: no cloud SPA; Worker HTML only |
| Preset | not applicable | — |
| Component library | none | Established pattern: consent.ts (SPINE-04) |
| Icon library | none — Unicode symbols only | No external asset deps in Workers |
| Font | system-ui, -apple-system, sans-serif | Mobile Safari default stack; no web font |
| Stylesheet | single `<style>` block inlined per page | CSP `style-src 'unsafe-inline'` already set in AUTH_SECURITY_HEADERS |

**Precedent:** `apps/atlas/src/auth/consent.ts` + `headers.ts` establish the project's
server-rendered HTML pattern. The Phase-4 confirm page follows the same skeleton: a
`renderXxx()` function returning a template-literal HTML string, served via the
`authHtmlResponse()` helper (which attaches the hardened security headers).

## Spacing Scale

Declared values (multiples of 4, applied as inline `style` attributes or a single `<style>` block):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gap, badge padding |
| sm | 8px | Button inner padding (vertical), label spacing |
| md | 16px | Default block padding, input padding |
| lg | 24px | Section gap, card padding |
| xl | 32px | Page-level top/bottom padding |
| 2xl | 48px | Separation between the artifact zone and controls |

Exceptions:
- Touch targets for Approve / Reject buttons: minimum **44px tall × full-width** (WCAG 2.5.5 AAA target size; mandatory on mobile Safari).
- Gap between Approve and Reject buttons: **24px** minimum — prevents fat-finger mis-tap. Approve
  is always BELOW the artifact; Reject is BELOW Approve. Order is intentional: the owner reads the
  artifact, then taps the action they mean. No side-by-side layout on mobile.

---

## Typography

Single font stack: `system-ui, -apple-system, "Segoe UI", sans-serif`. No web font loaded.

| Role | Size | Weight | Line Height | Usage |
|------|------|--------|-------------|-------|
| Body | 16px | 400 | 1.6 | Artifact text, labels, descriptions |
| Label | 14px | 600 | 1.4 | Section headers, field labels, platform names |
| Heading | 20px | 600 | 1.3 | Page title ("Review and confirm"), agent name |
| Mono | 14px | 400 | 1.5 | Exact post text rendered in `<pre>`, form field values |

**Rationale for mono body on artifacts:** The literal artifact (post text, form values) is
rendered in a `<pre>` / `<code>` element at 14px monospace so it reads as machine-generated
copy, not editorial copy — reinforcing "this is the exact text that will be posted."

Character count badge (Envoy/X only): Label size (14px, weight 600), rendered inline next to
the textarea as `NNN / 280`. Turns red (#B91C1C) at ≥ 270 characters.

---

## Color

Minimal two-tone palette. All values WCAG AA contrast (≥ 4.5:1 on their background).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFFFFF` (white) | Page background, card background |
| Secondary (30%) | `#F3F4F6` (gray-100) | Artifact zone background, field value blocks |
| Accent (10%) | `#1D4ED8` (blue-700) | Primary Approve button only |
| Destructive | `#B91C1C` (red-700) | Reject button, hard-stop banners, char-count overflow |
| Text primary | `#111827` (gray-900) | All body + heading text |
| Text secondary | `#6B7280` (gray-500) | Expiry countdown, metadata, help copy |
| Border | `#D1D5DB` (gray-300) | Input outlines, card borders, section dividers |
| Success | `#15803D` (green-700) | Post-approval confirmation states ("submitted", "PR opened") |
| Warning | `#B45309` (amber-700) | Hard-stop states (captcha, payment, sold-out) — text only |

Accent reserved for: the Approve button ONLY. No other interactive element uses blue-700.

**Color as a trust signal:** the page is intentionally low-color. No marketing gradients,
no hero imagery. The only bold color the owner sees is the Approve button (blue) and the
Reject button (red). This makes the intent of each tap unmistakable.

## Security Headers

Every confirm-page response MUST be served through the existing `authHtmlResponse()` helper
(or an equivalent), which attaches:

```
content-security-policy: frame-ancestors 'none'; default-src 'none'; style-src 'unsafe-inline'
x-frame-options: DENY
referrer-policy: no-referrer
cache-control: no-store
```

`default-src 'none'` means no external scripts, images, or fonts load. The page is
self-contained HTML + one inline `<style>` block. This is already established in the project
(`apps/atlas/src/auth/headers.ts`) and MUST be carried forward verbatim.

## Page Anatomy — Confirm Page

The confirm page has five zones, top to bottom:

```
┌─────────────────────────────────────┐
│  ZONE 1: Header strip               │  ~56px, gray-100 bg
│  "Atlas · [Agent]" + expiry badge   │
├─────────────────────────────────────┤
│  ZONE 2: What's about to happen     │  lg padding
│  Summary line + reversibility badge │
├─────────────────────────────────────┤
│  ZONE 3: Artifact zone              │  gray-100 bg, mono text
│  Exact post text / form values      │
│  [Edit textarea — if applicable]    │
├─────────────────────────────────────┤
│  ZONE 4: Metadata strip             │  sm text, gray-500
│  Price (Usher) / char count (Envoy) │
│  Platform / event / date            │
├─────────────────────────────────────┤
│  ZONE 5: Action controls            │  48px buttons, full-width
│  [Approve target]                   │
│  [Reject / Skip]                    │
└─────────────────────────────────────┘
```

**Zone 1 — Header strip:**
- Left: "Atlas" wordmark (text, gray-900, 14px weight 600)
- Right: expiry countdown badge — "Expires in 23h 47m" (gray-500, 12px). No color change until
  < 1h remaining, then amber-700. Renders a `<time datetime="ISO">` element.
- Strip bg: gray-100, no border-bottom (the artifact zone provides the visual break).

**Zone 2 — What's about to happen:**
- Single-sentence summary of the action (see Copywriting Contract below).
- Reversibility badge: a small inline pill rendered IMMEDIATELY to the right of the agent label.
  - "IRREVERSIBLE — you click Post" → red pill (#FEE2E2 bg, #B91C1C text) for LinkedIn/X posts.
  - "REVERSIBLE — PR / draft" → green pill (#DCFCE7 bg, #15803D text) for GitHub PR / README.
  - "REGISTRATION — auto-submits after confirm" → amber pill (#FEF9C3 bg, #B45309 text) for Usher.
- This badge is the PRIMARY legibility mechanism for depth-scales-with-reversibility (D4-08/09/10).
  It is NOT fine print; it is a first-class labeled element in Zone 2.

**Zone 3 — Artifact zone:**
- Background: gray-100 (secondary color).
- Rendered as `<pre style="white-space:pre-wrap; font-family:monospace; ...">` for post text.
- For Usher form values: a `<dl>` (definition list) with `<dt>` (field label, 14px/600) and
  `<dd>` (field value, 14px/400, mono). Price ALWAYS rendered as the first row, bold.
- For Envoy multi-target: each target is its own card (gray-100 bg, 1px border gray-300).
  Collapsed view shows the first 3 lines + "…expand"; a `<details>/<summary>` element handles
  this without JavaScript. Full text visible once expanded.
- Edit textarea: when present (Envoy targets), a `<textarea>` replaces the `<pre>` for that
  target after the owner clicks "Edit". Default hidden; a single inline JS event listener
  (`onclick="this.hidden=true; document.getElementById('edit-N').hidden=false"`) swaps them.
  This is the ONLY JavaScript on the page. If JS is disabled, the `<pre>` stays visible and the
  edit affordance degrades gracefully (owner can copy-edit in the ntfy notification chain).
- Character count for X: live character counter via `oninput` on the textarea (`NNN / 280`).
  Plain inline JS, no framework.

**Zone 4 — Metadata strip:**
- Usher: Price as `$XX.XX` or "Free", event name, date/time, location. Price in gray-900 weight
  600 (most important datum). Everything else gray-500.
- Envoy: Platform name, character count badge (X only), draft/PR indicator.
- Date/time always rendered in the owner's local timezone (America/Toronto) using `Intl`.

**Zone 5 — Action controls:**
- All buttons are `type="submit"` inside a `<form method="POST">` with `action="/confirm"`.
- Button placement: FULL WIDTH, stacked vertically. Approve on top, Reject below. 24px gap.
- Approve: 44px min-height, background blue-700, white text, weight 600. Rounded 6px.
- Reject: 44px min-height, background white, 1.5px solid red-700 border, red-700 text, weight 600.
- For Envoy multi-target: each target card has its own Approve / Skip controls.
  A "Confirm all approved" final submit button appears at the bottom ONLY after at least one
  target is approved. This prevents an accidental submit of an empty selection.
- After submission: the form is replaced by a static confirmation message (see post-decision
  states below). No spinner / no animation — plain text swap via a redirect to a
  `/confirmed?outcome=approved` route that renders the confirmation state page.

## Post-Decision States

Separate static pages rendered by the gate Worker after the form POST:

| Outcome | Heading | Body | Color signal |
|---------|---------|------|--------------|
| Approved (irreversible) | "Submitted to [Platform]" | "Your [post / registration] was submitted. No further action needed." | Success banner, green-700 |
| Approved (reversible) | "PR opened / README updated" | "The pull request is open at [URL]. No action needed." | Success banner, green-700 |
| Approved (Usher auto-submit) | "Registered for [Event]" | "Confirmation #[N] received. Calendar event added." | Success banner, green-700 |
| Rejected | "No action taken" | "You chose not to proceed. Nothing was posted or submitted." | Neutral — gray-900 text, no color banner |
| Expired | "This gate has expired" | "The confirmation window closed before a decision was made. Nothing was posted or submitted." | Neutral — gray-500 heading |
| Hard stop — captcha | "Manual step required" | "A CAPTCHA was detected. Complete registration at: [checkout link]" | Warning banner, amber-700 |
| Hard stop — payment | "Manual payment required" | "This event costs $XX.XX. Complete payment at: [checkout link]. Nothing was charged." | Warning banner, amber-700 |
| Hard stop — sold out | "Event is sold out" | "No registration was attempted. Nothing was charged." | Warning banner, amber-700 |
| Error | "Something went wrong" | "The gate encountered an error. No action was taken." | Neutral — gray-500 |

**All hard-stop and error states carry the explicit "Nothing was posted / submitted / charged"
line.** The owner must never have to wonder whether an action fired. This is the fail-safe
legibility contract.

## Envoy Multi-Target Layout

When Envoy fans into up to four targets, the confirm page renders them as a vertical list of
cards. Each card:

1. **Card header:** Platform name (Label, 14px/600) + reversibility badge (pill, as above)
   + character count badge (X only).
2. **Artifact zone:** `<pre>` or `<details>/<summary>` for long content.
3. **Per-target controls:** "Approve this target" (blue-700) / "Skip this target" (gray border).
   Skipping a target is not rejection of the whole batch — only the targets with Approve
   contribute to the final submit.
4. Once at least one target is approved, a "Confirm N approved targets" sticky button appears
   fixed at the bottom of the viewport. This is the ONLY sticky element on the page.

Per-target state is tracked in hidden `<input type="checkbox">` fields (no JS required for the
form submission itself; JS is only needed for the real-time character count and the edit swap).

## Usher Confirm Page Specifics

The single-card layout (one event, one gate) renders:

1. **Zone 2 summary:** "You're about to register for [Event Name]."
2. **Zone 3 artifact:** `<dl>` with rows in this fixed order:
   - Price: `$XX.XX` (or "Free") — FIRST, BOLD
   - Event: full event name
   - Date & time: owner-local formatted
   - Location: venue + address (or "Online")
   - Account: the email/identity Usher will use for registration (from Codex)
   - Notes: any form-field pre-fills extracted from the Codex (name, phone, etc.)
3. **Edit box is NOT present** for Usher — the artifact is structured data, not free text.
   If the owner wants to change any value, they Reject and edit in the Codex directly.
4. **Zone 4 metadata:** price repeated in gray-500 text beneath the artifact.
5. **Zone 5 controls:** "Register for [Event Name]" (Approve, blue-700) / "Don't register" (Reject).

### ntfy Push Notification Copy

| Field | Usher push | Envoy push |
|-------|-----------|-----------|
| Title | "Usher — registration pending" | "Envoy — publish pending" |
| Body | "Register for [Event Name] ($[XX] / Free) on [Date]? Review before it expires in 24h." | "Publish to [platform list] for [project slug]? Review drafts before they expire in 7d." |
| Action button 1 | "Review & edit" → opens confirm page URL | "Review & edit" → opens confirm page URL |
| Action button 2 | (none — registration needs review, D4-09) | (none — multi-target needs review) |

**Push body invariants:**
- NEVER include 2FA codes, password-reset links, or login URLs (security invariant, global).
- Always include: what will happen (post / register), which platform or event, expiry horizon.
- Always include price if nonzero (Usher).
- Cap body copy at 120 characters. Platform/event name truncated with "…" if needed.
- No Approve-in-push button for outward-irreversible actions (LinkedIn/X/Usher registration).
  The "Review & edit" link is the ONLY action. This prevents a single-tap accident on an
  irreversible public post. This is NOT a convenience omission — it is a deliberate friction gate.

## Interaction Contract

### Fail-Safe Defaults (visual manifestation of Pillar 2)

- **No button is pre-selected.** No default-checked approve. The form state on load is:
  zero targets approved, zero targets skipped.
- **The "Confirm N approved" button is hidden until at least one target is explicitly approved.**
  An empty-selection submit is unreachable.
- **No "approve all" shortcut.** Per-target approval only. The owner taps each target they want.
- **Timeout = expired, no action.** If the owner does nothing, the gate Worker's expiry-sweep
  cron transitions the row to `expired`. The confirm page, if still open, will return a 410 Gone
  on the POST, rendering the "This gate has expired" state.
- **Error = deny.** Any server-side error on the POST returns a 5xx and renders the "Something
  went wrong — no action taken" state. Never fail-open.

### Touch Target Rules

- Approve and Reject buttons: 44px min-height, full page width minus 32px horizontal margin.
- Minimum 24px gap between Approve and Reject (prevents fat-finger).
- Edit textarea activates via a "Edit this draft" text link (14px, blue-700 underlined), not a
  button — making it clearly secondary to Approve/Reject.
- The sticky "Confirm N approved" button on Envoy: 52px tall, bottom-safe-area-aware
  (`padding-bottom: env(safe-area-inset-bottom, 16px)`), full width.

### Focus States

All interactive elements carry a visible focus ring: `outline: 2px solid #1D4ED8; outline-offset: 2px`.
No `outline: none` anywhere. Required for keyboard and assistive-technology accessibility.

### Mobile-First Layout

- Max content width: 480px, centered.
- Horizontal padding: 16px (md) on the page body.
- Zone 3 artifact: horizontal scroll allowed (`overflow-x: auto`) for wide pre content.
- No horizontal breakpoint needed — the page is single-column on all viewports. Desktop gets the
  same layout; it just centers within a wider screen (not a desktop-optimized layout).
