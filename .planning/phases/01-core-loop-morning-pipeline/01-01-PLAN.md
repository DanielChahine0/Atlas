Output: an extended `apps/mcp-google/src/index.ts`, a new `apps/mcp-google/src/scopes.ts` (scope constants/predicates extracted from index.ts), and scope-floor + redaction tests for the new tools.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Agent → mcp-google (RPC/MCP) | Each agent presents an OAuth token carrying granted scopes; the server must enforce the per-tool floor, not trust the caller. |
| mcp-google → caller (tool output egress) | Gmail/Calendar bodies may contain 2FA codes / reset links / login URLs; they must be redacted server-side before egress. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-MCP-01 | Elevation of Privilege | new MCP tools | mitigate | Each tool checks its exact scope floor via scopes.ts predicate; returns forbiddenResult() (fail-closed) if absent. No tool assumes a broader scope. |
| T-1-MCP-02 | Information Disclosure | tool output egress | mitigate | Every tool funnels safeToolOutput() (redact + containsSecret → P1 block). 2FA/reset/login never escape regardless of scope (SPINE-04 backstop). |
| T-1-MCP-03 | Tampering / outward action | send/delete paths | mitigate | NO send, NO gmail-delete, NO calendar-delete tool registered — unreachable by construction (Pillar 2). |
| T-1-MCP-SC | Tampering | npm installs | accept | No new package installs in this plan (RESEARCH Package Legitimacy Audit: zero new deps). |
</threat_model>
